1. Executive Summary & Project Purpose

Urban traffic congestion is heavily exacerbated by motorists searching for available parking spaces, leading to lost time, fuel wastage, and increased urban carbon emissions. SpotSync is a full-stack, real-time parking discovery, advance reservation, and contactless ticketing platform designed to resolve urban parking friction for city centers, office hubs, and campus environments.

Built precisely according to the IEEE Std 830-1998 Software Requirements Specification (SRS v1.1), the application incorporates real-time WebSocket availability broadcast (<5 seconds propagation), transactional locking to eliminate double-booking, turn-by-turn GPS navigation with live ETA, cryptographically tokenized QR passes for contactless entry/exit gates, and automated fee computation based on actual stay duration.

2. System Features & SRS Requirement Traceability

The system encompasses six core functional feature groups mapped directly to SRS Section 4:

4.1 Search Parking Spaces by Location (REQ-1 to REQ-6)

  • Automatic Location Detection (REQ-1): Automatically senses user coordinates using the Geolocation API, centering the search on current position with default fallback to Sardar Patel Institute of Technology campus (19.1232, 72.8360).
  • Landmark & Destination Search (REQ-2): Text search allowing drivers to find lots near destinations (e.g., SPIT, BKC, Andheri, Lower Parel).
  • Interactive Leaflet Map & Card Views (REQ-3, REQ-4): Visual pins on OpenStreetMap indicating parking locations with real-time slot counters, paired with a toggleable list view.
  • Sorting & Radius Filtering (REQ-5): Configurable radius (1 km to 20 km) with instant sorting by distance (Haversine formula), hourly fee, or open slot count.
  • Auto-Radius Expansion (REQ-6): System automatically notifies the driver and expands the radius when no facilities fall within initial parameters.

4.2 Real-Time Parking Availability (REQ-7 to REQ-11)

  • Live Slot Counter (REQ-7): Accurately reports open spots against total capacity per facility.
  • WebSocket Propagation <5s (REQ-8): Changes in slot occupancy are pushed via bi-directional WebSockets to all connected client browsers in real time without polling delay.
  • Visual Color-Coded Indicators (REQ-9): Color-coded badges categorizing lots: Available (healthy capacity), Filling Fast (<30% remaining), and Full (0 slots).
  • Double-Booking Concurrency Lock (REQ-10): Database-level atomic transactions lock slot state during booking, resolving Risk R1 from the RMMM Plan.
  • Admin Maintenance Mode (REQ-11): Parking Lot Administrators can manually mark slots for maintenance or repair, instantly pulling them from public availability.

4.3 Slot Reservation & Cancellation Lifecycle (REQ-12 to REQ-17)

  • Specific Slot Selection (REQ-12, REQ-13): Interactive graphical matrix displaying individual spots (Standard 🚗, EV Charging ⚡, Accessible ♿, Compact 🏎️) for custom time windows.
  • Reservation History (REQ-14): Centralized log displaying active, checked-in, completed, and cancelled tickets.
  • Cancellation & Immediate Release (REQ-15, REQ-16): Drivers can cancel reservations prior to arrival, automatically returning the slot to the open pool.
  • 15-Minute Grace Period Background Monitor (REQ-17): Automated background worker detects unclaimed reservations 15 minutes past start time, cancels the pass, issues a notification, and frees the spot.

4.4 GPS Navigation & Routing (REQ-18 to REQ-21)

  • Turn-by-Turn Route Preview (REQ-18, REQ-19): Interactive polyline navigation overlay rendered directly inside the application.
  • Dynamic ETA & Distance (REQ-20): Displays remaining travel distance in kilometers and estimated arrival time based on urban transit speeds.
  • External Maps Integration (REQ-21): Direct link launching native Google Maps navigation with destination coordinates.

4.5 Contactless Digital QR Code Ticketing (REQ-22 to REQ-26)

  • Signed QR Generation (REQ-22): Cryptographically signs a unique token using HMAC-SHA256 immediately upon booking confirmation (SPOTSYNC:res_id:SIGNATURE).
  • Offline Caching (REQ-23): Passes are cached in browser localStorage, allowing drivers to display their ticket even when cellular reception is lost.
  • Gate Entry Validation (REQ-24): Lot admin scans QR pass at entrance gate, verifying token validity, marking ticket as entered, and recording exact arrival timestamp.
  • Gate Exit Scan & Automated Billing (REQ-25): Admin scans QR code at departure, records exit timestamp, calculates duration and billable hours, computes total fee, marks pass exited, and returns the slot to available pool.
  • Fraud & Replay Prevention (REQ-26): Explicit rejection of forged, expired, or already-consumed passes.

4.6 Real-Time Notifications (REQ-27 to REQ-30)

  • In-app alert banners and persistent notification drawer logging booking confirmations, 30-minute arrival reminders, and cancellations.
  • Profile preference toggles allowing drivers to configure which notification categories they receive (REQ-30).

3. Technical Architecture & Implementation Details

Architecture Philosophy
SpotSync implements a modular, decoupled full-stack architecture prioritizing sub-second latency, zero hardcoded logic, strict ACID data integrity, and cross-platform responsive UX.
Layer Technologies Used Key Responsibilities
Backend API Python 3.12, FastAPI, Uvicorn, Starlette RESTful endpoints, request validation, business logic, CORS, static file serving.
Real-Time Stream Native WebSockets (/ws/lots) Broadcasts slot state changes across all connected clients in < 5 seconds (REQ-8).
Database SQLite (WAL Mode, Foreign Keys ON) ACID transactions, relational schema (Users, Lots, Slots, Reservations, Tickets, Notifications).
Security PyJWT, HMAC-SHA256, SHA-256 Role-Based Access Control (RBAC), signed digital QR passes, password hashing.
Background Worker Asyncio Event Loop Task Periodically scans for grace period expiries (15 mins) and auto-releases abandoned slots.
Frontend Client HTML5, Tailwind CSS, Lucide Icons Modern glassmorphism mobile-first SPA, interactive slot matrix, notification drawer.
Mapping & GPS Leaflet.js & OpenStreetMap Interactive pins, custom color-coded badges, routing polyline, distance calculation.
QR Engine QRCode.js (Client) + HMAC (Backend) Vector QR rendering, offline storage, camera/manual validation gate portal.

Data Model & Referential Integrity (Appendix B.2)

  • users: Primary key user_id, role-based classification (driver, lot_admin, sys_admin, guest), notification settings.
  • parking_lots: Stores facility name, address, latitude/longitude coordinates, pricing per hour, and total slots.
  • slots: Relational child of parking_lots. Tracks slot_number, vehicle type (standard, ev, accessible, compact), and live status (available, booked, maintenance).
  • reservations: Relational bridge linking user, slot, lot, scheduled start/end windows, and booking status (active, checked_in, completed, cancelled, expired).
  • tickets: 1-to-1 relationship with reservations. Contains signed QR code, entry timestamp, exit timestamp, fee amount, and gate status.
  • notifications: User-specific alert history with category tagging and read/unread flags.

5. Key Viva Questions & Model Answers

Question Model Technical Answer
How does SpotSync prevent two users from booking the same slot at the same time? We utilize SQLite atomic transactions with BEGIN IMMEDIATE locking. When a reservation request arrives, the slot's current status and active reservation records are checked inside the locked transaction. If another user commits first, the second transaction is immediately rolled back and returns an HTTP 409 Conflict error.
How do you achieve real-time availability updates across clients? Instead of client-side polling, the backend maintains a WebSocket connection pool (/ws/lots). Whenever a slot changes state (booked, cancelled, entered, or maintenance), the server broadcasts a lightweight JSON payload to all active clients within 100 milliseconds, fulfilling REQ-8 (<5 seconds).
How are QR codes protected against forgery and reuse? Each QR token embeds the reservation ID, user ID, and slot ID signed with HMAC-SHA256 using a server secret key. Upon scanning, the server recalculates and verifies the cryptographic signature, verifies that the ticket is in the correct state, and marks it as consumed to prevent replay attacks.
How does the system calculate parking fees upon exit? Upon entry scan, the server records the exact UTC entry timestamp. Upon exit scan, the departure timestamp is logged and the duration is computed in seconds. Hours are rounded up to billable increments multiplied by the lot's rate per hour, ensuring accurate pricing.
How is offline ticketing achieved? Whenever an online reservation is confirmed, the ticket payload and cryptographic token are serialized and cached in browser localStorage. Even if the driver loses internet connection in an underground garage, the pass renders offline directly from local storage.
